# ТЗ: отдельный виджет 'АИ-агент КП'

Заказчик: ООО 'РУС ДВЕРИ'. Аккаунт amoCRM 28528549 (aleksnevedrov.amocrm.ru).
Дата: 12.10.2026. Исполнитель: Claude Code в репозитории /opt/ai-door/src.

## 1. Цель

Развести два продукта, которые сейчас живут в одном виджете:

- 'АИ-продавец' - переписка с клиентами, задачи менеджерам, база знаний, каталог;
- 'АИ-агент КП' - разбор запросов, поиск цен, сборка коммерческого предложения.

Менеджер должен видеть два разных инструмента, а не один с вкладками на все случаи.

## 2. Принятые решения заказчика (12.10.2026)

| Вопрос | Решение |
| --- | --- |
| Куда идёт КП | в отдельный виджет 'АИ-агент КП' |
| Что с кодом КП в агенте | вырезать полностью |
| Чистка кода | обязательна, раздел 7 |
| Процессы api и worker | остаются общими (на сервере свободно ~709 МБ RAM) |
| База данных | общая, таблицы kp_* уже отдельные |
| Почта | остаётся входом агента, граница в разделе 4 |

## 4. Граница между агентом и КП

Два места нельзя разрезать пополам - у них разводится зона ответственности.

| Место | Остаётся агенту | Уходит в КП |
| --- | --- | --- |
| Почта (packages/mail) | забрать письмо, сохранить вложения, распознать признак 'запрос КП' (kp-request.ts), поставить примечание в сделку | разбор спецификации, подбор позиций, поиск цен, сборка документа |
| Клиент amoCRM (packages/amo) | общий, им пользуются оба | ничего не дублируется |

Почта - это вход. Она помечает сделку и больше ничего про КП не знает.
Агент после работ не содержит ни одной строки, собирающей КП.

## 5. Этап 2. Новый виджет 'АИ-агент КП'

Новое приложение apps/widget-kp со своим package.json и своим манифестом.

| Параметр | Значение |
| --- | --- |
| Название в amoCRM | АИ-агент КП |
| widget_code | новый, не совпадает с виджетом агента |
| Версия на старте | 1.0.0 |
| Размещение | карточка сделки и страница настроек |
| Состав | блок КП в сделке, настройки КП, черновики, история сборок |
| Адрес API | тот же, https://ai.rf-dveri.ru |
| Ожидаемый размер архива | 40-50 КБ (сейчас общий архив 161 КБ) |

Общий код ДВУХ виджетов (базовый клиент API, авторизация, стили, общие типы,
хелперы вроде useLead) выносится в общий пакет packages/widget-core.
Копировать api.ts и стили во второй виджет запрещено.

Сборка: существующий образ ai-door-build, команда по аналогии с виджетом агента,
результат - apps/widget-kp/dist/widget.zip. В nginx добавить постоянную ссылку
вида /dl/widget-kp-XXXX.zip (как у агента - /dl/widget-9f2c.zip), чтобы адрес не менялся.

Правило версий действует и здесь: перед каждой выдачей архива поднять version
в package.json, иначе amoCRM отдаст старый код.

## 7. Чистка кода (требование заказчика)

Разделение делается НЕ копированием. После каждого этапа код должен стать
меньше и проще, а не больше.

Что не должно остаться в агенте после вырезания:

| Мусор | Как проверяется |
| --- | --- |
| Неиспользуемые импорты и переменные | eslint без ошибок по затронутым пакетам |
| Мёртвые ветки и недостижимый код | ручной просмотр диффа |
| Поля типов и ключи настроек от КП | grep по 'kp' и 'Kp' в packages/agent и apps/widget |
| Методы API-клиента, которые больше никто не вызывает | то же |
| Тесты на удалённый функционал | прогон тестов |
| Закомментированный код и файлы-заглушки | ручной просмотр |
| Ненужные зависимости в package.json | сверка с фактическими импортами |

Правила нового кода:

1. Ни одного скопированного файла между виджетами. Если код нужен обоим -
   он уезжает в packages/widget-core, а не живёт в двух местах.
2. Один источник правды для констант КП: таблица kp_settings.
   Дублировать гарантию, условия оплаты и прочее в коде или в базе знаний запрещено.
3. Перенос файла - это git mv и правка импортов, а не 'создать копию, старый оставить'.
4. Функции длиннее 80 строк при переносе разбивать, а не перекладывать как есть.
5. Комментарии на русском, по делу, только где поведение неочевидно.
6. После каждого этапа в коммите указать: сколько строк добавлено и сколько удалено.

Заодно починить известный долг, если файл и так правится: 7 ошибок eslint
в apps/worker/src/wazzup-dump.ts и packages/db/src/wazzup-dumps.ts.
Если файл не затрагивается работой - не лезть, отдельным коммитом и по согласованию.

## 8. Этап 4. База знаний КП

Отдельная от базы агента (knowledge_items, 32 документа - не трогать).

Вид содержимого - справочные материалы, а не готовые блоки текста: готовые
блоки уже есть в константах kp_settings (sellerName, sellerRequisites, vatRate,
paymentTerms, warranty, delivery, validDays, coverLetter, signature) и вставляются
шаблоном kp.docx.

Состав на старте (загружает заказчик):

| Документ | Зачем |
| --- | --- |
| Прайс на доставку по зонам | расчёт строки доставки под адрес |
| Прайс на замер и монтаж | то же |
| Регламент работы с юрлицами и тендерами | формулировки под ТКП |
| Замены и аналоги фабрик | подбор, когда точной модели нет |
| Стоп-лист: что не поставляем и чего не обещаем | защита от вымысла |

Технически: таблица kp_knowledge_items (отдельная миграция), поле usage
со значениями reference (справка) и block (готовый текст) - на старте у всех
документов reference. Вкладка загрузки в виджете КП.
В генерацию КП справки подмешиваются только как исходные данные; выдумывать
цифры, которых в них нет, запрещено.

## 11. Запреты

1. Не менять поведение агента в переписке с клиентами - ни одного шага.
2. Не трогать: триггеры Salesbot, почту агента, парсер форм, приёмник вебхуков Wazzup,
   фиды Яндекс 'Товары и цены' 4375722, 4865958, 4865959.
3. Комплектующие в фидах Яндекса не участвуют - логику каталога не менять.
4. Не менять боевые данные напрямую в Postgres - только через миграции и код.
5. Автоотправки КП нет: документ собирается и уходит только после подтверждения менеджера.
6. Цены комплектующих - из карточки двери (door_components), общих цифр не подставлять.

## 13. Ограничения работы

- Боевой деплой (docker compose build / up) и push выполняет заказчик через /root/push.sh.
  В конце каждого этапа дать список команд в нужном порядке.
- Порядок всегда: миграция, сборка образов, перезапуск api и worker, потом настройки.
  docker compose up -d не пересоздаёт контейнер без build.
- Перед push: git fetch и rebase.
- Ресурсы сервера: свободно ~8,7 ГБ диска и ~709 МБ RAM. Новых постоянных процессов не добавлять.
- Ключ OpenAI - в account_secrets (kind = openai), в логи и интерфейс не попадает.
- Перед правками показывать схему с цифрами; id писать вместе с названием; данные - таблицами.
