# ТЗ: автоматический поиск рыночных цен для КП

Заказчик: ООО «РУС ДВЕРИ». Дата: 12.10.2026. Аккаунт amoCRM 28528549.

## 1. Цель

Агент получает заявку с техническим описанием, исследует публичные розничные цены рынка Москвы и МО,
рассчитывает стоимость и автоматически заполняет черновик КП. Дилерские кабинеты не требуются.

## 3. Этап 1. Веб-поиск в слое модели

Файлы: `packages/llm/src/types.ts`, `packages/llm/src/openai.ts`.

1. В `ChatRequest` добавить `hostedTools?: ('web_search')[]` и `toolChoice?: 'auto' | 'required'`.
2. В OpenAI-адаптере при `hostedTools` включать в тело запроса:
   - `tools: [{ type: 'web_search' }]` (плюс наши function-tools, если есть);
   - `tool_choice: 'required'` — когда `toolChoice === 'required'`;
   - `include: ['web_search_call.action.sources']` — всегда при веб-поиске.
3. В ответе собирать `sources: { url, title?, snippet? }[]` из item’ов `web_search_call` и возвращать в `ChatResponse.sources`.
4. Если провайдер ответил ошибкой на `web_search` или инструмент не вызван ни разу — бросать ошибку
   `WebSearchUnavailableError` с текстом провайдера. Запрещено молча продолжать без поиска.
5. Антропик-адаптер (`anthropic.ts`): при `hostedTools` бросать понятную ошибку — веб-поиск только у OpenAI.

Тесты: тело запроса содержит нужные поля; источники разбираются из фикстуры ответа; при пустом списке
вызовов поиска летит `WebSearchUnavailableError`.

## 4. Этап 2. Модуль исследования цен

Новый файл: packages/kp/src/market-research.ts (новый пакет, агент его не импортирует)

Вход: позиция спецификации (наименование, фабрика, модель, размер, покрытие,
комплектность, количество), регион поиска, настройки КП аккаунта.

Шаги:

1. Сборка поискового запроса из полей позиции. Если фабрика и модель не заданы,
   запрос строится по наименованию и характеристикам, результат помечается низкой
   уверенностью.
2. Один вызов модели с hostedTools ['web_search'] и toolChoice 'required'.
   Регион поиска: Москва и Московская область, вся розница, без списка разрешённых сайтов.
3. Ответ модели - строгая JSON-схема (outputSchema), массив предложений:
   url, seller, title, price, currency, unit, quantityInUnit, inStock, foundAt, vatStated.
   unit - одно из: piece (полотно), set (комплект), m2 (квадратный метр).
4. Фильтр соответствия товара. Предложение отбрасывается, если:
   - тип не совпадает (полотно против дверного блока);
   - единица продажи не приводится к единице нашей позиции;
   - размер отличается больше допуска (по умолчанию 0 мм, настраивается);
   - цена отличается от медианы остальных больше чем в 3 раза (выброс).
   Каждое отброшенное предложение сохраняется с причиной - это нужно в интерфейсе.
5. Приведение к одной единице. Для m2 - умножение на площадь полотна из спецификации,
   для set - деление на quantityInUnit. Формула приведения сохраняется строкой.
6. Статистика по оставшимся: минимум, максимум, медиана, число источников.
7. Порог достоверности: меньше 3 подтверждённых предложений - статус insufficient,
   цена не подставляется, в интерфейсе выводится 'мало источников'.

Ошибки не глотаем: если веб-поиск недоступен, наверх уходит WebSearchUnavailableError
с текстом провайдера. Модуль не выдаёт цену 'по памяти модели'.

## 5. Этап 3. Хранение результатов

Миграция в packages/db/migrations. Новая таблица kp_price_research:

| Поле | Тип | Назначение |
| --- | --- | --- |
| id | bigserial | ключ |
| account_id | bigint | аккаунт amoCRM |
| draft_id | bigint null | черновик КП, если исследование запущено из него |
| item_key | text | ключ позиции внутри черновика |
| query | text | фактический поисковый запрос |
| status | text | ok / insufficient / failed |
| offers | jsonb | все предложения с признаком accepted и причиной отклонения |
| stats | jsonb | min, max, median, count, unit |
| error | text null | текст ошибки при status = failed |
| model | text | модель и версия, которой сделан поиск |
| cost_usd | numeric | стоимость вызова |
| created_at | timestamptz | дата исследования |

Индексы: (account_id, draft_id), (account_id, created_at).
Репозиторий KpPriceResearchRepo рядом с KpRepo: save, listByDraft, getLatestByQuery.
Кэш: повторный запрос с тем же query в течение 7 дней берёт сохранённый результат,
в интерфейсе показывается дата и кнопка 'Искать заново'. Срок жизни кэша - настройка.

## 6. Этап 4. Цена предложения и НДС

Главное правило: найденная рыночная цена и наша цена предложения - два разных поля.
В КП клиенту уходит только наша цена, рыночная видна только менеджеру в виджете.

Правило цены КП хранится в настройках КП; таблица pricing_rules и пакет pricing агента не меняются. До ответа заказчика (раздел 11)
реализовать базовый вариант: скидка от медианы розницы в процентах, одна на весь аккаунт,
значение в настройках КП, по умолчанию 0 (цена равна медиане). Код пишется так,
чтобы правило было отдельной функцией и замена его не требовала правки остального.

НДС берётся из настроек КП (сейчас vatRate = 22) и применяется только к нашей цене.
Статус НДС у найденных цен хранится как есть в поле vatStated: included / excluded / unknown.
До ответа заказчика предложения с unknown не пересчитываются, в интерфейсе стоит пометка
'статус НДС неизвестен'.

Все суммы - целые копейки, округление на последнем шаге, без накопления погрешности.

## 7. Этап 5. API и автозаполнение черновика

Файл apps/api/src/routes/widget-kp.ts.

Новые маршруты:

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | /widget/kp/research | исследование одной позиции или списка позиций черновика |
| GET | /widget/kp/research?draftId= | история исследований по черновику |

Поиск идёт через очередь, не в запросе: один вызов веб-поиска занимает десятки секунд,
а позиций в спецификации бывает десятки. POST ставит задание и сразу возвращает список
идентификаторов, интерфейс опрашивает GET раз в 2-3 секунды. Очередь - новая, kp-research,
параллельность 2, чтобы не выбить лимиты провайдера. Обработчик в apps/worker.

Автозаполнение: после успешного исследования в черновик КП пишутся три поля позиции:
рыночная медиана, наша цена по правилу, ссылка на запись исследования.
Статусы insufficient и failed ничего в черновик не пишут: позиция остаётся пустой,
с пометкой для менеджера.

Уже заполненную вручную цену автозаполнение не затирает без явного подтверждения в интерфейсе.

## 8. Этап 6. Интерфейс виджета

Файлы apps/widget/src/KpBlock.tsx и apps/widget/src/KpSettings.tsx.

В KpBlock у каждой позиции:

- кнопка 'Найти цены' и кнопка 'Найти цены по всем позициям' сверху;
- состояние: идёт поиск / найдено N источников / мало источников / ошибка с текстом;
- сворачиваемый список источников: продавец, цена, единица, дата, ссылка;
- отклонённые предложения показываются отдельно с причиной - менеджер видит, что отброшено;
- диапазон и медиана отдельной строкой;
- наша цена редактируется вручную, при правке ставится пометка 'изменено менеджером'.

В KpSettings добавляются: включение веб-поиска, регион, минимум источников (по умолчанию 3),
срок жизни кэша в днях (7), скидка от розницы в процентах (0), допуск по размеру в мм (0).
Схема настроек strict: сначала деплой кода, потом сохранение настроек, иначе unrecognized_keys.

## 9. Запреты

1. Не выдумывать цены. Цена без ссылки и даты не сохраняется и не показывается.
2. Не выдумывать остатки, сроки поставки и сертификаты. Если источник их не даёт - поле пусто.
3. При неработающем веб-поиске показывать конкретную ошибку провайдера, а не пустой результат
   и не цену из знаний модели.
4. Не трогать: триггеры Salesbot, почту агента, парсер форм, приёмник вебхуков Wazzup,
   фиды Яндекс 'Товары и цены' 4375722, 4865958, 4865959.
5. Комплектующие не участвуют в фидах Яндекса - логику каталога здесь не менять.
6. Не менять боевые данные напрямую в Postgres - только через миграции и код.

## 10. Тесты и приёмка

Автотесты (vitest, без сети, провайдер замокается):

- адаптер OpenAI: tools и tool_choice уходят в запрос, sources собираются из ответа;
- модель не вызвала инструмент - WebSearchUnavailableError, а не пустой ответ;
- фильтр соответствия: полотно против блока, штука против комплекта, квадратный метр;
- приведение единиц и расчёт медианы на чётном и нечётном числе источников;
- отсечение выбросов;
- меньше трёх источников - статус insufficient, цена в черновик не попадает;
- расчёт нашей цены и НДС на целых копейках;
- кэш: повторный запрос в окне кэша не дёргает провайдера.

Приёмка на живом примере: взять одну реальную заявку с разобранной спецификацией
(сделка 89835, файл 'Двери (3).docx', 11 позиций) и показать таблицей:
позиция, число источников, диапазон, медиана, наша цена, статус.
Критерий: по позициям с известной фабрикой и моделью - не менее 3 источников,
каждый открывается по ссылке и показывает тот же товар, цена совпадает с сохранённой.

## 11. Открытые вопросы к заказчику

Ответы будут позже. До них делать базовые варианты из раздела 6 и держать оба места
отдельными функциями, чтобы замена правила была правкой одной функции.

1. Правила цены предложения. В pricing_rules одна запись. Как считать нашу цену
   от найденной розницы: фиксированная скидка от розницы (%), наценка на закупку,
   разные правила по фабрикам или ручная правка каждой позиции?
2. НДС в найденных ценах. Розница на сайтах почти всегда с НДС, но статус продавца
   не всегда известен. Что делаем: считать цену источника как 'с НДС' по умолчанию,
   или всегда помечать 'статус неизвестен' и показывать обе суммы?

## 12. Ограничения работы

- Боевой деплой (docker compose build / up) и push выполняет заказчик.
  В конце работы дать готовый список команд в нужном порядке.
- Порядок всегда такой: миграция, сборка образов, перезапуск api и worker,
  и только потом сохранение новых настроек в виджете.
  docker compose up -d не пересоздаёт контейнер, если образ не изменился - нужен build.
- Ключ OpenAI хранится в таблице account_secrets (kind = openai), в коде берётся через secrets.get.
  В логи и в интерфейс ключ не попадает.
- Перед правками показывать схему с цифрами; id писать вместе с названием;
  данные выводить таблицами.
- Работать ветками, не писать прямо в основную. Каждый этап - отдельный коммит.

## 13. Порядок работ

Этапы 1-2 дают работающий поиск и проверяются на одной позиции из консоли -
это тот самый 'работающий сценарий на одной заявке', с которого просил начать заказчик.
Дальше 3-4 (хранение и расчёт), потом 5-6 (API и интерфейс).
Показывать результат после каждого этапа, не копить всё до конца.

## 14. Изоляция от агента (главное требование)

Работа только для раздела КП. Поведение AI-агента в переписке с клиентами
не меняется ни на шаг. Агент никогда не делает веб-поиск и не видит рыночных цен.

Чего не касаемся вообще:

| Что | Где |
| --- | --- |
| Конвейер ответов агента | packages/agent/src/pipeline.ts, orchestrator.ts |
| Проверки допуска, пауза, групповые чаты | packages/agent |
| Автопостановка задач и вечерний обход | packages/agent/src/task-sweep.ts |
| Расчёт цен агента | packages/pricing, таблица pricing_rules |
| База знаний агента | knowledge_items (32 документа) |
| Настройки агента | все блоки настроек, кроме блока КП |
| Триггеры Salesbot, почта агента, парсер форм, вебхуки Wazzup | - |

Два места, где пересечение всё же есть, и условия к ним:

1. Пакет packages/llm - общий, его импортирует и агент. Правки только добавляющие:
   новые необязательные поля hostedTools и toolChoice в ChatRequest. Не переданы - запрос
   уходит байт в байт таким же, как сейчас. Старые сигнатуры не менять, поведение
   по умолчанию не менять. Отдельный тест: вызов без hostedTools даёт тот же запрос,
   что до правки.
2. Процесс worker - общий. Новая очередь kp-research отдельная, свой обработчик,
   своя параллельность. Очередь maintenance и её 8 плановых джоб не трогать.

Новый код живёт в отдельном пакете packages/kp. Импорт этого пакета из packages/agent
запрещён - это проверяется при приёмке (grep по импортам).

Проверка на приёмке: прогнать существующие тесты агента - должны пройти без правок;
отправить тестовое сообщение в диалог - ответ агента такой же, как до работ.
