## Что сделано

| Пункт | Где | Содержание |
| --- | --- | --- |
| 1. Категория позиции | `packages/opt/kb/src/category.ts` (`detectCategory`, `categoryOf`, `componentKindOf`), `packages/opt/kp/src/draft.ts` (`KpRequestItem.category`, `KpLine.category`, `lineCategory`, `isServiceLine`), `table-parse.ts` | `door` / `component` (коробка, наличник, добор, порог, притворная планка, капитель) / `hardware` (замок, цилиндр, накладки, ручка, петля, доводчик, защёлка, фиксатор, шпингалет…) / `service` (монтаж, демонтаж, установка, врезка, разгрузка, погрузка, доставка, подъём, сборка, замер, работы, услуги). Правило: работы, комплектующие и фурнитура — только по первым словам названия (главное существительное впереди), дверь — по слову в любом месте; иначе «Аква 01 ПГ + УПД … /врезка замка под цилиндр…» из заявки 30008823 становилась работой (нашлось на 10 позициях файла). Без ключевых слов («Турин») — дверь. Категория ставится при разборе письма и спецификации и хранится в позиции и строке черновика; у старых черновиков без поля считается по тексту. Работы по-прежнему `kind = service`: без размера, без поиска цены, после товаров |
| 2. Реалистичность по категории | `prices.ts` (`categoryMedian`), `research-job.ts` | медиана для фильтра 40–300 %: двери — по совместимой группе признаков среди дверей; комплектующие — по строкам своего вида (все «Добор (…)»); фурнитура — по строкам с тем же первым словом («ручка …»). Группы нет — фильтр не применяется. «Добор телескопический, МДФ» больше не отбрасывается по медиане дверей 21 100 ₽; в пометке теперь «медиана прайса по группе «комплектующие» …». Та же проверка при подборе веб-записей из базы |
| 3. Колонки «Коробка / Наличник / Добор / Порог» | `price-list.ts` (`ColumnMapping.components`, `extractPrices`, `draftsToPrices`), `prices.ts` (`kb_prices.category`, `component_kind`), миграция `008_kb_price_category.sql` | при импорте прайса дверей из каждой такой колонки создаётся отдельная запись «Коробка (ДВ CPL)» с категорией комплектующее, видом, покрытием и признаками двери (материал, покрытие), без размера, описание «комплектующее к ДВ CPL»; у двери в нескольких размерах — одна запись на модель. Цена двери — только из колонки «Цена» / «Стоимость». Позиция категории комплектующее ищет цену только среди таких записей своего вида: по признакам (покрытие, материал) — «Коробка дверная CPL» → «Коробка (ДВ CPL)»; без указания двери — самая дешёвая из подходящих с пометкой «комплектующее по прайсу: Добор (ДВ ПВХ) — модель двери в заявке не указана, взята самая дешёвая строка». Веб-поиск — только если в прайсе таких строк нет. Счётчик «прайс: цен N» у файла теперь включает строки комплектующих |
| 4. Прайс фурнитуры | `core.ts` (`defaultCategoryOfPriceKey`), `category.ts` | «Прайс_фурнитура…xlsx» импортируется как прайс дверей (колонки «Наименование», «Артикул/размер», «Цена»; ключ по имени файла, замена своих цен, удаление файла — только его цены); строки без ключевых слов получают категорию фурнитура по имени файла. Позиции категории фурнитура ищут цену только среди записей фурнитуры (по ключу, словам, синонимам); строки дверей не мешают |
| 5. Работы | `build.ts` (`SERVICE_NOTE`, `service_note`, `withServiceNoteFallback`), `kp-build.ts`, виджет | в таблицу КП и «Итого» работы не входят; под таблицей абзац «Стоимость монтажных работ рассчитывается после замера дверных проёмов.» — во всех КП, где есть хоть одна работа: плейсхолдер `{{service_note}}`, а в шаблоне без него — строкой под фразой о ценах, иначе под строкой НДС (у шаблона заказчика есть `{{vat_phrase}}`), иначе под плашкой. Сборка требует цены у всех позиций, кроме работ. В журнале `kp_build` «работ вне таблицы: N». В виджете у работы пометка «работы — по замеру: в таблицу и итог КП не входят…», поле цены с подсказкой «по замеру», «Итого» и кнопка «Собрать документ» работы не учитывают |
| 6. Все позиции за одно нажатие | `apps/opt-api/src/routes/kp.ts`, `research-job.ts` (`RESEARCH_BATCH = 20`, `ResearchJob.batch/batches`), виджет | `POST /kp/research` «по всем» ставит все позиции без цены (кроме работ), в очередь порциями по 20 подряд; ответ `{queued, total, batches}`; при двух и более порциях запись в журнале «Поиск цен: поставлено позиций 113 порциями по 20 (6)». Лимит `maxPositionsPerRun` (30) остался только для автопоиска при сборке. Виджет показывает на кнопке «Ищу цены… 32 / 136» (обработано / поставлено) и по завершении перечитывает черновик |
| 7. ДПГ / ДПГУЧ / Аква из черновика 57 | — | причина по коду: `POST /kp/research` «по всем» ставил не больше `maxPositionsPerRun` = 30 позиций без цены за нажатие — из 113 обрабатывались первые 30, остальные (в том числе ДПГ/ДПГУЧ/Аква ниже по списку) до поиска не доходили. Вторая причина у «Аква … /врезка замка…» — категория «работы» по слову «врезка» (п. 1). После п. 1 и п. 6 все 113 ставятся за одно нажатие; «Аква 01 ПГ + УПД … /врезка замка под цилиндр…» подбирается к строке «Аква 01 ПГ» прайса по вхождению слов (проверено тестом). Если какое-то из 6 наименований не подберётся и после этого — нужны точные названия строк прайса и позиций, сверю ключи |
