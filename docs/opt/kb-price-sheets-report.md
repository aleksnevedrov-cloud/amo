виджет 1.2.1. Розница и ядро не менялись (`git diff 06d538d -- packages/retail apps/api apps/worker apps/widget packages/core` = 0).

**Важное допущение.** Файлы «Прайс_межкомнатные_двери_ГОСТ.xlsx» и «Прайс_металлические_двери_ГОСТ.xlsx» в сессию не

`kb_index` будет «неизвестные колонки — пропущены» / «неизвестная вкладка — пропущена» или причина отмены импорта с листом,
строкой и колонкой. Прошу положить настоящие файлы в `docs/opt/price-samples/` — прогоню разбор на них и, если нужно, поправлю
регулярные выражения шапок одним коммитом.

| 2. Нестандарт по сетке | `packages/opt/kb/src/book-pricing.ts` (`nonstandardBySizes`), `prices.ts` (`lookupPrice`) | для строк многолистового прайса вместо правил записи: точное совпадение с размером модели (строго, 1 мм — уже нестандарт) — 0 %; любое отличие (и меньше) — +30 %; ширина ИЛИ высота больше эталона строго более чем на 30 % — +100 % вместо 30 %; ровно 30 % — остаётся 30 % (ALU-005 1950×2375 при 1500×2700 → 70 200). Один коэффициент только к базе двери; комплектующие и фурнитура не индексируются. Эталон — ближайший размер той же модели (наименьшее относительное отклонение по большему измерению; при равенстве — по сумме отклонений): 899×2000 при 800 и 900 → 900×2000, 1171×2000 → 900×2000 (+30,1 % — крупный). Геометрия: `pair` — сумма ширин створок, `each_leaf` — самая широкая створка, `overall_pair` — габарит. Пометки: «нестандарт 899×2000 при эталоне 900×2000: +30 % к базе», `production_note` файла (или «Нестандартные позиции подлежат уточнению на производстве.»), у противопожарных ещё «размер и огнестойкость исполнения уточняются» — все три идут и в КП под позицией |
| Основание размера | `lookupPrice` | проём / полотно / блок / пара различаются, автоконвертации нет: если у модели есть сетка, а основание в ID не указано — пометка «основание размера в прайсе не указано (проём / полотно / блок) — уточнить у менеджера»; если основание заявки (`PriceQuery.sizeBasis`) расходится с прайсом — базовая цена без пересчёта и вопрос менеджеру |
| 3. Цена и смета | `price-book.ts` (`estimateFromComment`), `lookupPrice` | цена — с листа 1; нет цены, но в комментарии / «Входит в базу» правило сборки («полотно INT-005 8 800 + коробка 3 160 = 11 960» или сумма слагаемых) → сметная цена, статус `estimate_only`, пометка «сметная цена: … — для сметы, уточнить у менеджера», в виджете «сметная цена». Товар без цены и без правила — пропуск с записью в журнал |
| Статусы | `lookupPrice` (`allowed`) | `inactive` (ALU-003/004) и `estimate_only` (INT-008, ALU-007) в обычный подбор по признакам не попадают; берутся только когда позиция названа прямо (точный ключ модели или синоним) либо в режиме сметы (`PriceQuery.estimate`), всегда с пометкой. Модель, названная целиком («ДПГ сота с коробкой» = INT-008), стоит выше подбора по признакам и не отвергается расхождением признаков |
| 4. Компоненты по модели двери | `lookupPrice` (`doorsByProductId`, `PriceQuery.doorProductId`), `research-job.ts` (`doorContextOf`) | для комплектующего / фурнитуры контекст — ближайшая дверь заявки выше (её `product_id`; если дверь ещё без цены — подбирается по базе тут же). Статус компонента у этой двери: `included` → «входит в цену блока ДВ CPL», цена 0, в таблицу КП и итог не идёт (исправление «самой дешёвой строки» KB-COMPONENTS); `not_priced` → «уточнить у менеджера: добор к ДВ CPL в прайсе без цены», цена пустая (не 0); `priced` → строки комплектующих именно этой модели («Коробка (ДВ CPL)» 3 160). Без двери в заявке — прежний подбор своего вида с пометкой |
| Фурнитура | `lookupPrice` (`forDoor`, `hardwareIncluded`), `research-job.ts` (`hardwareSetOf`) | «Для моделей»: при известной двери берётся только подходящая ей; без двери — любая, с пометкой «фурнитура для моделей …». Тариф или название из «Входит в базу» / комментария двери (ALU-005 — фрамуга OPT-024, MET-012 — вентиляционная решётка OPT-018) → «входит в цену блока». Комплект (OPT-025 «Включено: 2×OPT-029, 2×OPT-030, OPT-031») в той же группе двери: входящие тарифы, названные отдельно, не удваиваются («входит в комплект «…» — отдельно не считается»); OPT-003 включает ручки и цилиндр (OPT-028) тем же механизмом. «Уточнить» тарифа (OPT-008 → «нужен стеклопакет OPT-009») — пометка менеджеру. Количество — по позиции заявки, как и раньше |
| Категория по синониму | `category.ts`, `lookupPrice` | слова типов фурнитуры из «Дополнений» (фрамуга, вентиляционная решётка, крепёж, уплотнитель, стеклопакет, задвижка, цепочка, шумоизоляция, окраска, комплект фурнитуры / петель) добавлены в ключевые слова фурнитуры; если позиция по словам «дверь», но её точный ключ или синоним ведёт к строке другой категории — категория берётся из строки прайса, плитка и таблица КП следуют за ней |
| 5. Пары | `core.ts`, `book-pricing.ts` | пара — одна базовая позиция (строка двери с `leaves = 2` по «Створок» / геометрии); нестандарт пары — по ширинам створок из `kb_sizes.leaf_widths_mm` |
| 6. Документ КП | `packages/opt/kp/src/kp-build.ts`, `build.ts` (`quote_note`, `priceText`), `draft.ts` (`KpLine.priceOutcome`, `quoteNotes`, `productId`, `includedIn`, `kpShortName`) | «входит в блок» — не строка таблицы: под дверью «В цену блока входит: Порог», для комплектов «В составе комплекта «Комплект петель и крепежа»: Петля накладная»; «в прайсе цены нет» — строка с «уточнить у менеджера» вместо цены, сумма «—», в итог не входит; примечания из «Подбора» и фразы нестандарта — под позицией (`{{quote_note}}` в строке таблицы шаблона; без тега — строками под названием, как комплектация).
