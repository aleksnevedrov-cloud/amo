# Этап 1 — каркас, БД, API чатов amoCRM, виджет, Telegram-бот

## Что сделано

| Пункт ТЗ | Реализация |
|---|---|
| 2. Отдельный проект | Папка `rf-messenger/`: свой workspace, lock-файл, Dockerfile, `docker-compose.yml` (свои postgres и redis, порт только 127.0.0.1:3100). Пакеты AI-агента не используются |
| 2. connectors / bridge / api / widget | Процессы `api` и `connectors`; мост `bridge.ts`; виджет `widget/` |
| 2. БД | `channels` (ключи и сессии зашифрованы), `chats`, `messages` (статусы, цитаты, автор в группе), `files`, `amojo_connections` |
| 2. Очередь | BullMQ: `to-amo` и `to-channel`, 10 попыток с экспоненциальной паузой, jobId = id сообщения (без дублей) |
| 3.2 Подключение канала | Кнопка в виджете → `POST /v2/origin/custom/{channel_id}/connect` → `scope_id` |
| 3.3 Входящее | `POST /v2/origin/custom/{scope_id}` с `X-Signature` (HMAC-SHA1), `conversation_id` = наш id чата |
| 3.4 Исходящее | `/amojo/v1/hook/:scope_id`: проверка подписи за постоянное время, дубль вебхука отсекается по id сообщения amo |
| 3.5 Статусы | После отправки — «доставлено», при ошибке — «ошибка» с причиной (`delivery_status`) |
| 3 «с телефона» | Поддержано в мосте (sender — менеджер, receiver — клиент); у Telegram-бота таких сообщений нет, используется с этапа 2 |
| 4. Telegram-бот | Текст, фото, файлы, видео, голосовые, стикеры; группы (имя автора в тексте); цитаты в обе стороны; длинные тексты по частям |
| 4. Файлы | Хранятся в `/data/files`, в amo — ссылка `https://chat.rf-dveri.ru/f/…` на 30 дней; после срока — 410 |
| 5. Виджет | Список каналов и статусы («Подключён», «Нет связи с телефоном», «Сессия завершена — нужен новый QR / вход», «Ошибка»), подключение бота по токену, отключение; только администратор; токен после сохранения не показывается |
| 6. Защита от блокировок | Пауза 1–3 с между исходящими в чат и «печатает…»; переподключение — экспоненциально, не чаще раза в 30 с; рассылок нет: отправка только ответом в существующий чат |

## Отличие от ТЗ

«По процессу на каждое подключение»: на этапе 1 все боты работают в одном процессе `connectors`
(бот — это один HTTP-запрос раз в 25 с, отдельный процесс на бота съел бы ≈ 90 МБ RAM). Сбой одного
бота пишется в его статус и не останавливает остальные. Для WhatsApp и Telegram личного (этапы 2–3)
каждая сессия будет отдельным дочерним процессом под управлением `connectors`.

## Проверка

| Команда | Результат |
|---|---|
| `pnpm lint` | без замечаний |
| `pnpm typecheck` | без ошибок |
| `pnpm test` | server: 35 тестов, widget: 4 теста — все зелёные |
| `pnpm build` | `server/dist/{api,connectors,migrate}.js`, `widget/dist/widget.zip` (9 файлов, script.js 7 КБ) |
| Запуск собранных процессов с локальными PostgreSQL и Redis | `/health` → `{"ok":true,"db":true,"redis":true}`; API виджета без токена → 401; вебхук без подписи → 401 |

Что покрывают тесты: подпись запросов amojo и вебхука; повтор события канала и вебхука amo не создаёт
дублей; вложение хранится у нас и уходит подписанной ссылкой; группа и цитата; сообщение «с телефона»
как исходящее; пауза перед отправкой; «доставлено» и «ошибка» в amo; вложение из amo только с домена amo;
изоляция аккаунтов в API виджета; одноразовость токена; только администратор; токен бота зашифрован и не
возвращается; ссылки на файлы: подделка → 403, просрочка → 410; разбор обновлений Telegram; переподключение.

## Память

Факт RSS локально: api ≈ 95 МБ, connectors ≈ 98 МБ. Оценка и лимиты контейнеров — `docs/deploy.md`.

## Приёмка этапа 1 (на сервере, после регистрации канала amo)

1. Сообщение тестовому боту → чат в сделке «Неразобранное» воронки «Двери».
2. Ответ менеджера из amoCRM → приходит в Telegram, в amo статус «доставлено».
3. Фото клиент → amo (открывается по ссылке chat.rf-dveri.ru) и amo → клиент.
4. Проверить, что шаг Salesbot «Отправить сообщение» в чате нашего канала уходит в Telegram.
